# Records and linking

Read live headers and dropdowns before writing. Edit Pipeline and Decision Register Master, plus the Decision Register's Options tab for your own proposed decision; other tabs there are views or belong to other writers (the planner writes the Pipeline's Steps tab). Find every row by its permanent ID immediately before writing it, never by row position, title or a row number read earlier: other runs and the founder may add, sort or move rows in between.

Keep longer cell text readable. In Pipeline Summary / Why, Next step / Research question and Revisit trigger, and Decision Register Question, Reason and Rework instructions, put distinct points on separate lines and numbered steps on separate lines. Use actual line breaks in cell values, not literal `\n` characters or one run-on paragraph. A single short thought can stay on one line. Preserve founder-written line breaks when revising a cell, and read back multiline values after saving.

- [Pipeline](https://docs.google.com/spreadsheets/d/1aL678ACs97YpLIGrGU5LbpXHc7jQBxl64ED-sLyehvI/edit): permanent numeric ID; optional External ID; domain/entity, title, scope, status, Stage and Review stage. Current decision ID selects the active decision; ClickUp Pipeline URL identifies its UI task; Document count is derived from the Index. Removed link columns must not be recreated. Agent type Manual is skipped by scheduled agents; Ready is selection, not execution permission.
- [Document Index](https://docs.google.com/spreadsheets/d/1kObhQNjsFhziS-wRzjaEIzr9j8jjbfvd-ZgvzuwQ-Jc/edit): find an existing row by Drive file ID/URL and keep its permanent numeric Document ID; a new file gets a reserved ID. Associate each document with Pipeline ID, Pipeline title and Related Pipeline URL where those live fields exist. Use the revision/sequence field and Supersedes document ID for substantive replacements; retain originals. An original plan and an assessment may both belong to one Pipeline item without either superseding the other. Every deliverable lives in Drive, in the Agent output folder that fits and from the template that fits, and Drive URL is its Drive link. Never put a GitHub link in Drive URL. Copy exact field names and dropdown values from the live sheet.
- [Decision Register](https://docs.google.com/spreadsheets/d/1_megp_hD4gwRuF4wmk4g2vQGAWbLl4uNUpho-oLoygE/edit): permanent numeric Decision ID, Pipeline ID/title, evidence links, affected plan, reason, decision/status, Review stage and Rework instructions. Multiple decisions can refer to one Pipeline item. Only explicit founder choices are accepted decisions. Proposed decisions have no invented acceptance date. Preserve history and supersedes references.

**Research Links holds Drive files only:** Google Docs, Sheets or Slides, or an HTML file saved in Drive, one link per line. Never a GitHub link (compare, commit, branch, pull request or repository file), a Drive folder or a web page. Evidence that lives in a repository, such as a planning note or a diff, gets a Drive document first, from the template that fits, that copies or summarises it and names the repository, branch and commit; the repo file stays in the repo, and its GitHub link goes in that document's Related Repo Document in the Document Index. Web sources are cited inside the Drive document, not in Research Links.

A deliverable about a target repository can also get a repo doc, but only when that repository already keeps its own docs (a docs folder or another place its owner uses). Follow its structure, naming and templates. If it has no such place, add nothing and create no folder. Commit to the item's GitHub branch, after verifying the remote and branch; if that field is blank, use the working branch you were given. Never assume `main`. The repo doc names the Drive document by Document ID, and the Drive document wins on conflict. Related Repo Document is the GitHub link on that branch, blank when there is no repo doc; when the item is completed and its branch is merged, update the link to the merged location if you know it. Do not change a target repository's CLAUDE.md, AGENTS.md or similar agent instructions to record Horology workflow.

Decision and Document IDs are permanent numeric IDs, independent in each register; never renumber or reuse them. Reserve each new ID and check ownership before every write as below. External IDs and Drive file IDs remain separate identifiers.

## Register IDs and ownership

Decision and Document IDs come from the document-graph connector, never from the sheet. Parallel runs share these registers, so counting up from the highest ID in the sheet lets two runs pick the same ID and the later write silently replaces the other run's row.

1. **New row:** read the register's highest ID, then call `reserve_id(register, pipeline_id, run_id, live_max_id)` with register `decision` or `document`, the Pipeline ID, your run ID (from `claim_item`, e.g. R-12) and that highest ID. Use exactly the returned `id` in the row and anywhere else it appears (document metadata, the Pipeline's Current decision ID, Next step text). Reserve one ID per row, before you first write it anywhere; an unused reservation is simply skipped, never reused.
2. **Before every write, new row or update:** find the row by its ID (never by row position, title or a remembered row number), then call `check_register_write(register, id, pipeline_id, drive_url, live_pipeline_id, live_drive_url, live_row_exists)` with what you are about to write and what the live row holds now. `drive_url` is required for the Document Index. For a Decision Register write that sets Research Links, pass the links as `research_links`; `ok: false` with reason `research_links_not_drive` lists the links that are not Drive files, so replace them before writing.
3. **`ok: false` means stop.** The ID already belongs to another Pipeline item or Drive file. Don't write, overwrite or "fix" that row; reserve a new ID for your own row if you need one, and report the clash in your summary.
4. Read the row back after writing and confirm its ID, Pipeline ID and Drive URL.

If the connector is unavailable, don't allocate IDs: save the Drive output, leave the register rows unwritten and report them as pending.

## Proposed decisions and options

The decision page reads options from the Decision Register's **Options** tab, not from the Decision cell.

- **Decision** (Master): one line, for example `Proposed: Option B, lead with intermediate lifters.` Detail stays in the document; Reason holds the evidence and key figures, one point per line.
- **Options** tab: one row per option the founder can choose, with columns Decision ID, Code, Summary, Recommended and Key figures. Code is a capital letter (A, B, C) in the order the document presents them. Summary is one plain line. Recommended is `Yes` on the recommended option only, blank otherwise. Key figures is optional: cost, effort, reach or thresholds, one per line. Park and reject are outcomes on the page, not options.
- Write the Master row first, then its Options rows. Find existing rows by Decision ID and Code, never by position. `check_register_write` for the Decision ID covers its Options rows; don't touch another decision's rows. On rework of your own proposed decision, update its rows in place and blank the Summary of an option you drop.
- If the workbook has no Options tab, write the options in the Decision cell as `Option A …; Option B …` and report that the tab is missing.

Metadata carries domain, entity, Pipeline ID/link, purpose, draft status and related decision when applicable. Domain and Entity come from the Domains tab, and folders and templates from Locations and Templates ([domains, folders and templates](locations.md)). Copy templates; preserve originals. Follow the [presentation rules](presentation.md).

Rows with Graph Inclusion TRUE are copied into the document graph by the sync job, which writes Graph Sync Status back. Graph Inclusion is the founder's choice: don't set it yourself, and don't claim a document is in the graph until its status says `synced`. Platform skills, Drive access and scheduling must each be configured separately.
