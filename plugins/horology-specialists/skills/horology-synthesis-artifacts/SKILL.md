# Horology Synthesis Artifacts

The supervisor invokes this specialist as the final step of a Stage 3 run, on both routes. On the investigation route the source is the Stage 3 specialist deliverable; on the implementation route (Feature, Enhancement, Refactor, Fix) it is the Implementation report Google Doc, and the artifact is a page that shows what was done. Stage 4 needs no new founder prompt, Ready selection or schedule. The item is Completed when the artifact is saved; the founder reviews the combined Stage 3 deliverable and Stage 4 artifact afterward and can reopen the item from its decision. This skill does not accept a proposal, authorise implementation or send email.

## Inputs and ownership

1. Receive the Pipeline ID and active run ID from the supervisor. The supervisor owns `claim_item` and `finish_run`; do not claim or finish that run again. For a standalone recovery request, first check the live row and Document Index, then claim and finish exactly one separate run.
2. Read the live Pipeline, Decision Register and Document Index by header name, and find rows by their IDs, never by position. Read the Stage 3 deliverable, prior investigation, earlier decisions and source documents. Prefer the latest nonsuperseded documents. Treat a proposed decision as **pending founder review**; never present it as accepted.
3. Check the Synthesis folder and the Document Index workbook's Pages tab for a Stage 4 artifact already made for this Pipeline ID and its current Stage 3 deliverable or Implementation report. Reuse a verified artifact instead of duplicating it. If the source changes materially, save a new version beside the old one in Drive and keep the old file.
4. Read [locations](../horology-research/references/locations.md) and the Pipeline Locations tab. Use only the Synthesis folder for the item's Domain and Entity; place supporting assets in its Assets folder.

## Visual briefing

5. Lead with the proposed outcome, the decision the founder needs to make and the current status. Prefer a self-contained HTML briefing when it can be saved and opened reliably. Use a visual Google Doc, Sheet or a useful combination when that serves the material better. Keep the first view brief: a clear headline, a simple process or comparison graphic, three to five evidence cards, the main tradeoff and the next action. Put detailed rationale, uncertainties and source links lower down or behind expandable sections. Design for mobile and print, with readable contrast and text alternatives for visual meaning. Do not create a text-heavy document and call it a visual synthesis.
6. Use images or charts when they clarify the evidence or comparison. Python is allowed for chart generation: choose a chart that answers the actual question, make it legible and visually polished, and export a static SVG or high-resolution PNG that works in HTML and print. Use real figures only where sources support them; label units, dates, estimates and uncertainty. Do not invent measurements or draw a chart from qualitative claims. Bundle permitted source images and chart assets with the HTML rather than relying on temporary third-party or private Drive image URLs. Provide alt text and source attribution. Follow [visual and private publishing guidance](references/visuals-and-pages.md).
7. Show what Stage 1 found, what Stage 2 authorised, what Stage 3 produced, the proposed choice and any unresolved question. For an implementation item, build the page from the Implementation report: what changed and why, the commits and pull request, the tests, changes from the Stage 1 plan, and what's left for the founder; there is no Stage 2. The report and Stage 1 documents remain the record. Include direct links to source documents and Decision Register. The artifact is a presentation of the work, not a new recommendation or decision.
8. Save and verify every principal output in the matching Synthesis folder, with the Pipeline ID and current decision ID in its file name. A Stage 4 HTML page gets no Document Index row and no reserved Document ID (decided by the founder on 04/11/2026): it is kept in Drive so it can be republished, and the Pages tab lists the published page. Its source, the Stage 3 deliverable or Implementation report, is the indexed document. A visual Google Doc or Sheet used instead of HTML is a document: register it in Document Index under a Document ID reserved with `reserve_id` (register `document`, the Pipeline ID and the supervisor's run ID), after `check_register_write` confirms the ID is free or already this file's ([register ID rules](../horology-research/references/linking.md)), with Graph Inclusion FALSE (only the founder changes it); stop and report if the check fails. A proposal remains `draft` until the founder approves it. Do not create or change a Decision Register decision.
9. When the founder's private Cloudflare Pages project and deployment access are configured, offer the HTML briefing at a stable, Access-protected URL following [the publishing procedure](references/visuals-and-pages.md). Keep the Drive HTML as the saved copy and the source document as the record, and list the page on the Document Index workbook's Pages tab after a verified publish, with the source document's Document ID. Publishing is optional: an unavailable or unverified Pages setup must not prevent a verified Drive synthesis or Stage 4 transition. Never publish through a public Pages URL or widen an Access policy to make deployment work.
10. Return verified Drive and, if published, private Pages links plus unresolved gaps to the supervisor. The supervisor then proposes the Specialist deliverable decision, makes it the Current decision ID and moves the item directly from Stage 3 to **Stage 4**, Status **Completed**, Review stage **Specialist deliverable**, Agent status **No action**, keeping the substantive Next step (`synthesize-stage-3`, or `complete-implementation` on the implementation route). Only advance after the Drive outputs are verified. If synthesis creation fails, leave Stage 3 in place and report the failure; report a publishing failure separately.
