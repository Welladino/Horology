# Research Brief

## Topic
- cron-script-security-pattern

## Question
- The document graph has a real gap: `write_document` and `auto_link_similar_documents` are two separate tool calls, not one atomic operation, so a document can be written and never embedded/linked if an agent forgets the second call or it errors. Fixing this needs a periodic sweep that checks for unembedded documents and backfills them. The founder does not want an agent to be able to execute arbitrary code to do this check. What's the right way to run a cheap, safe, recurring "is there anything to backfill" check, and what credential/access boundary should it have?

## Summary
- Hermes's own cron scheduler supports a `script` field with `no_agent=True`, which runs a script on schedule and delivers its stdout directly, **skipping the LLM entirely** when there's nothing to escalate — this is a Hermes-native mechanism, not something we'd be bolting on.
- This is fundamentally different from giving an *agent* `code_execution`/`terminal` (already disabled on every profile, including Second-Soul, per `docs/architecture/system_overview.md`): the script's content is authored and reviewed by us ahead of time, like `docker-compose.yml` or an Alembic migration, not generated by a model at runtime. No profile's tool permissions change to support this.
- Hermes explicitly sanitizes the script's subprocess environment — "provider API credentials and other Hermes-managed secrets are not inherited by cron scripts" (confirmed from the official docs, see Sources) — so the script cannot piggyback on any existing Hermes- or MCP-server-managed credential. It needs its own, separately-provisioned credential.
- Two candidate designs for that credential were considered: Neon's Data API (HTTPS/JWT-based) vs. a dedicated read-only Postgres role reached via a plain connection string. The Postgres role is the better fit here — see Findings/Recommendation.

## Sources
- Hermes cron docs: `https://hermes-agent.nousresearch.com/docs/user-guide/features/cron` (fetched via WebFetch, 2026-08-07) — confirmed script runtime selection (`.sh`/`.bash` under bash, else the current Python interpreter), `no_agent=True` behavior, `context_from` chaining via `~/.hermes/cron/output/{job_id}/*.md`, and the credential-sanitization behavior.
- Bundled local reference: `hermes-data/skills/autonomous-ai-agents/hermes-agent/references/background-systems.md` — thinner than the official docs (names the `script`/`no_agent`/`context_from` knobs but doesn't cover runtime user, network reach, or credential handling); consulted first but insufficient to design against alone.
- Neon Data API docs: `https://neon.com/docs/data-api/get-started` (fetched via WebFetch, 2026-08-07) — confirmed it's REST-style filtering (`.select()`/`.eq()`/`.limit()`/`.rpc()`), not arbitrary SQL; requires JWT auth with a `sub` claim; RLS is "strongly recommended but technically not mandatory" and without it "authenticated users can view all rows"; distinct from Neon's separate project/branch management API.
- This project's own existing pattern: `document-graph-mcp` and `github-monitor-mcp` each hold their own scoped credential in their own container's environment, never sharing Hermes's — confirmed in `docs/architecture/system_overview.md` and `docs/runbook/mcp/README.md`.
- Attempted but not completed: hands-on verification via `docker exec` into the running `horology-hermes` container (to confirm script runtime user/network reach directly, matching this project's standing "verify hands-on" practice) — Docker Desktop was not running at the time, so this fell back to the official docs site instead. **Flagged as an open gap, not a substitute for real verification** — see Open Questions.

## Findings
- **`no_agent=True` is a real free-tier**: stdout goes straight to the delivery target (or, via `context_from`, into the next chained job's prompt) with zero model inference. This is exactly the "cheap daily check, only pay for an agent turn when there's something to do" shape wanted.
- **Script location/execution is constrained but simple**: scripts must live in `$HERMES_HOME/scripts/`, referenced by relative filename only (no absolute/`~` paths outside that directory). Extension picks the runtime — `.py` runs under Hermes's own `sys.executable`, no shebang needed.
- **Credential sanitization is a real, documented security boundary already provided by Hermes**, not something we need to build: cron scripts do not inherit Hermes-managed secrets (provider API keys, etc.) by default. This means whatever the script needs to read the database, it needs its own explicit credential — it cannot accidentally piggyback on Hermes's own OpenRouter key or any MCP server's `DATABASE_URL_POOLED`.
- **What's still undocumented, even from the official page**: the exact container user/privilege level the script runs as, and whether it can reach other services on the same Docker network (e.g. calling `document-graph-mcp:8765` directly as an HTTP client). Neither the official docs nor the bundled skill doc address this.
- **Neon Data API, evaluated as an alternative to a DB role**:
  - Pro: pure HTTPS, no DB driver needed in the script.
  - Con: REST-style filtering, not arbitrary SQL — our actual query (`documents` LEFT JOIN `document_embeddings` WHERE embedding IS NULL, an anti-join) is not a simple filter; whether the Data API's relationship-embedding filters can express this cleanly is unconfirmed and would need its own verification pass.
  - Con: needs JWT issuance (a `sub` claim, RLS policy setup) — meaningfully more moving parts than handing the script a connection string.
  - Con: RLS is optional but its absence is explicitly flagged as a real gap in Neon's own docs ("authenticated users can view all rows") — for a single-purpose script this is probably fine, but it's a weaker, less-tested enforcement boundary than a database-level GRANT.
  - Con: enabling the Data API is a project-wide toggle, a new surface turned on for the whole Neon project rather than something scoped narrowly to this one script's need.
- **Dedicated read-only Postgres role, evaluated as the alternative**:
  - Uses the exact same connection pattern already used everywhere in this repo (`psycopg2`, a `DATABASE_URL`-style env var) — the script's DB code can mirror `document-graph-mcp`'s own tiny `_connect()` helper almost verbatim.
  - Enforcement is a database GRANT (`GRANT SELECT ON documents, document_embeddings TO <role>;`) — cannot write, full stop, at the engine level. No JWT/RLS configuration to get subtly wrong.
  - Zero new project-level surface enabled on Neon.
  - Fits the existing "every credential-holder gets its own narrowly-scoped credential" pattern already established for both MCP servers.

## Recommendation
- Use a dedicated **read-only Postgres role** on the same Neon project, granted `SELECT` only on `documents` and `document_embeddings` (the two tables the sweep's query touches), with its own connection string in its own env var — not inherited from Hermes, not shared with `document-graph-mcp`'s own (read-write) credential.
- Script is a small `.py` file under `$HERMES_HOME/scripts/`, using `psycopg2` with that read-only connection string, running the LEFT JOIN/anti-join query, printing the resulting ids (plain text/markdown, since `context_from` prepends raw stdout into the next job's prompt — not JSON unless we choose to format it that way ourselves).
- Cron job configured with `no_agent=True` when nothing is found (script exits with empty output, no escalation); when ids are found, `context_from` chains into a Second-Soul job that calls the existing `auto_link_similar_documents(id)` MCP tool per id — no new profile, no `code_execution`/`terminal` re-enabled anywhere.
- Do not use the Neon Data API for this — better suited to cases needing HTTP-native access with no DB driver available at all, which isn't our constraint (the script already runs inside a Python interpreter that can just use `psycopg2`).

## Open Questions
- Container user/privilege level and Docker-network reach for cron scripts were never confirmed hands-on (Docker wasn't running at research time) — worth a real `docker exec` check before this ships, per this project's standing "verify hands-on" practice. Low risk to the recommendation above either way, since the read-only-role design doesn't depend on network reach to `document-graph-mcp` — it talks to Neon directly.
- Exact stdout format contract for `context_from` (confirmed to be read from `~/.hermes/cron/output/{job_id}/*.md` and prepended to the next job's prompt) should be verified live once the stack is up — specifically, whether multiple ids need a specific delimiter/format for Second-Soul to parse reliably, or whether a plain one-per-line list is enough given it's just prepended as agent-readable context, not machine-parsed.
- The read-only role's exact grant (table-level vs. column-level, whether `document_embeddings` needs SELECT at all if the script only queries `documents`+`document_embeddings` via a join) should be finalized against the real schema when implementing, not just this brief's sketch.
