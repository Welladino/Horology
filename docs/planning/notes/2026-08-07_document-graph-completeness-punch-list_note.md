# Implementation Note

## Topic
- document-graph-completeness-punch-list

## Context

Follow-up to `2026-08-06_auto-link-similar-documents_note.md`. That work shipped `auto_link_similar_documents` but left two things unaddressed: (1) nothing reads the `document_links` graph it builds — no tool surfaces relationships back to an agent or the founder; (2) `write_document` and `auto_link_similar_documents` are separate tool calls with nothing enforcing the second always follows the first, so a document can silently end up unembedded (agent forgot, or the call errored) with no way to notice short of manual SQL. A conversation on 2026-08-06/07 worked through the design for both gaps, plus adjacent questions (how the similarity graph actually behaves at moderate document counts, whether topic tagging is worth adding, and how to stop near-duplicate analysis documents from flooding the founder). This note is the resulting punch list — decisions made, and what's still open — before implementation starts.

## Decision

**Build now:**

1. **`get_related_documents(document_id)`** — new tool on `document-graph-mcp`. Reads `document_links` (outgoing + incoming edges) joined to `documents` for title/type. Closes the "edges exist but nothing reads them" gap — today the only way to see the graph is manual SQL, same as how the original auto-linking work verified itself.

2. **`list_unembedded_documents()`** — new tool on `document-graph-mcp`. `documents` LEFT JOIN `document_embeddings` WHERE embedding IS NULL, no parameters (expected result size is small; this is a maintenance check, not a browsing tool). Returns `{id, title, doc_type, created_at}` per row. Feeds item 3.

3. **Daily backfill sweep, via Hermes's native cron `script` + `no_agent` mode** — full design in `docs/planning/research/2026-08-07_cron-script-security-pattern_research.md`. Summary: a `.py` script under `$HERMES_HOME/scripts/`, using a **dedicated read-only Postgres role** (its own credential, `SELECT` only on `documents`/`document_embeddings`, provisioned separately from `document-graph-mcp`'s own read-write credential) to run the same query as item 2. Runs daily; if empty, `no_agent=True` delivers stdout with zero LLM cost; if non-empty, `context_from` chains into a Second-Soul job that calls the existing `auto_link_similar_documents(id)` tool per id. No new profile — matches the earlier decision that this sweep doesn't need judgment, just mechanical retry.

4. **Near-duplicate signal at write time** — persona instruction change, no schema/tool change. When `auto_link_similar_documents`'s `newly_linked` includes a similarity score at or above a second, higher bar (proposed ~0.95, not yet tuned against real data), the calling persona should say so explicitly in its `kanban_complete` summary ("near-duplicate of doc #N") rather than letting it look like an ordinary `related_to` edge. Start with `code-sentinel` specifically, since daily-recurring analysis is the concrete case that motivated this (its reports risk high similarity from template structure alone, independent of substantive novelty).

**Explicitly decided not to build:**

- **No new "document-linker" or similar profile for the sweep.** Second-Soul already has `cronjob` and document-graph tool access; the sweep's escalation step is a bare tool-call loop with zero judgment involved, which doesn't justify a new persistent identity.
- **No topic tagging.** Embeddings already solve the semantic-matching goal (finding related content across agents/wording) that tagging would target, without needing a taxonomy that would need constant upkeep across an open-ended, multi-agent document set.
- **No retroactive re-comparison sweep for already-embedded documents.** Traced through the mechanics for a 25-document scenario: because `auto_link_similar_documents` compares each new document against every existing embedded document at write time, the design already self-heals without needing to re-run old pairs — a later document's own call is what catches a similarity to an earlier one, symmetric and one-directional-trigger by construction. No gap here.
- **No agent gets `code_execution`/`terminal` re-enabled to support the sweep.** The cron `script` step is authored/reviewed by us ahead of time (same trust tier as `docker-compose.yml` or an Alembic migration), not generated by a model at runtime — this is not the same category of risk as giving an agent a code-execution tool, and no profile's toolset changes because of it.

## Rationale

Every choice above followed the same test already established in this project: does the mechanical, judgment-free part of the work need an LLM turn at all? The `no_agent` sweep, the decision against a new profile, and the decision against a retroactive re-scan all reduce to the same answer — no, so don't spend a turn (or a new persistent identity) on it. The read-only-role-over-Neon-Data-API choice (full reasoning in the linked research brief) followed the same standing practice as the original auto-linking work: verify the actual constraint (script credential sanitization, Data API's REST-only query shape) before designing around an assumption, rather than reaching for "Neon has an API" as a reason to skip a real comparison.

## Impact

- Two new tools on `document-graph-mcp` (`get_related_documents`, `list_unembedded_documents`) — additive, no changes to the four existing tools.
- One new cron job plus one new Neon Postgres role (read-only) — new infrastructure, but scoped narrowly and following the existing "every credential-holder gets its own credential" pattern.
- Persona text changes for near-duplicate signaling — starts with `code-sentinel`, extend to others if the same daily-recurring pattern shows up elsewhere.
- No changes to any profile's tool/cap configuration (`code_execution`, `terminal`, `cronjob` grants stay exactly as they are today).

## Follow-Ups

- Container user/privilege level and Docker-network reach for cron scripts were never confirmed hands-on (Docker wasn't running during the research pass) — verify via `docker exec` once the stack is up, before this ships. Low risk to the chosen design either way, since it talks to Neon directly rather than depending on reaching `document-graph-mcp` over the internal network.
- The 0.85 auto-link threshold and the proposed ~0.95 near-duplicate threshold are both unvalidated against real volume — revisit once `code-sentinel` has run daily for a week or two and there's real data to check for over-clustering from template-structure similarity rather than genuine content similarity.
- `context_from`'s exact stdout format contract (plain text prepended into the next job's prompt, per the research brief) should be checked live once implemented — specifically whether a plain one-id-per-line list is sufficient for Second-Soul to parse reliably.
- The read-only role's exact grant scope (whether `document_embeddings` needs its own SELECT grant alongside `documents`, given the query is a join across both) should be finalized against the live schema during implementation, not assumed from this note.

## Status (as of 2026-08-07, later same day)

All four items built. Recorded here rather than editing the Decision section above, since that describes what was decided, not a running status.

- **Items 1 & 2** (`get_related_documents`, `list_unembedded_documents`) — shipped on `document-graph-mcp`, tested (23/23 unit tests passing), deployed to the running container, confirmed live via `hermes mcp test document-graph` (7/7 tools discovered).
- **Item 3** (daily sweep) — shipped, but the mechanism differs from what's described above: no `context_from`/two-job chain — the real `hermes cron create` CLI doesn't expose that flag. Used the `wakeAgent` gate instead (a script's final stdout line of `{"wakeAgent": false}` skips the agent for that run; anything else wakes it with the script's stdout injected into its prompt) — same cost profile, one job instead of two. Full detail in `2026-08-07_document-graph-embedding-sweep_note.md`. Live cron job `document-graph-embedding-sweep` (`2ba96135728f`), daily 09:00 UTC, verified against the real database.
- **Item 4** (near-duplicate signaling) — added to `CLAUDE.md`'s document-creation conventions (applies to any subagent) and reinforced in `personas/subagents/code-sentinel.md` specifically (the concrete recurring-report case), synced to the running container. Threshold set at 0.95, per the original proposal — still unvalidated against real volume, per the Follow-Up above.
